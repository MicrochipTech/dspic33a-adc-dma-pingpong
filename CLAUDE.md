# Working on this repository (AI coding agents and humans)

A bare-metal demonstration example for the dsPIC33AK512MPS512 on the EV74H48A
(dsPIC33 Curiosity Platform Development Board, GP DIM), with a second profile for the
EV17P63A Curiosity Nano (MPS506). The whole repository is measured against one sentence:

> **At a sample rate you choose, the ADC streams samples through the DMA into RAM
> continuously, and the CPU processes them on the free half of a ping-pong buffer.**

Four parts - *chosen rate*, *continuously*, *through the DMA*, *CPU processes* - and they
are not equally far along. Do not describe the example as working without reading
`docs/ANALYSIS.md` first.

## Core, glue, lab

| Part | Folders | Meaning |
|---|---|---|
| core | `src/drivers/`, `src/port/`, `src/lib/`, `src/core/` | what a customer takes into their own project |
| glue | `src/app/`, `src/boards/` | what a customer writes for their own board |
| lab | `src/lab/`, `src/sim/` | what this repository adds on top: self-tests, benches, back-to-back mode, simulator stand-ins |

**Rule: nothing under `src/core/`, `src/drivers/`, `src/port/`, `src/lib/` includes a header
from `src/lab/` or `src/sim/`.** The core reaches the lab only through weak hooks with a
do-nothing default: `cli_register_lab()` (cli.c), `adc_ch0_event()` (adc.c), the
application hooks `sigproc_app_*()` (`sigproc.h`), `sigproc_app_cmd()`/`sigproc_app_status()`
(`console.h`), `gui_link_app_fields()` (`gui_link.h`), and on the PC side the optional
`gui_app` module next to `tools/adc_gui.py`. `tools\build.bat core` proves the rule: `src/lab`
and `src/sim` are not on that build's include path and `src/core/example_main.c` replaces
`main.c`. Every folder is on the include path of every build, so sources include each other
as `"name.h"` without a folder prefix; file names are unique across the tree.

## Driver and board rules

- Nobody outside `dma.c` touches a DMA register, nobody outside `adc.c` an ADC register,
  nobody outside `clock.c` reads `CLK1CON`, nobody outside `uart.c` touches a UART register.
- A driver under `src/drivers/` logs, waits and panics only through `src/port/`
  (`port_log()`, `port_log_kv()`, `port_trace*()`, `port_flush()`, `PORT_WAIT_WHILE()`,
  `port_panic()`), never `console_*`, `WAIT_WHILE()` or `fail()`, and includes none of
  `console.h`, `diag.h`, `capture.h`. What it needs from the application it asks for
  through a hook declared in its own header (`clock_fail_hook()`).
- Register dumps do not print: `xxx_regs_visit(visit)` hands each register to the caller's
  `reg_visit_t` (`port/regs.h`); `diag.c`'s `reg_print()` prints. `uart.c` is the one
  exception to the port-layer paragraph (it is what the console writes through).
- Board data: a driver gets a board-specific value through a parameter of its own
  `*_init()` or keeps it a `board.h` macro, never `board_cfg.h` directly. `board_cfg` is read
  only by the application layer. Wider moves (ADC core/input, LED pin, console PPS) were
  tried and reverted; `src/boards/board_cfg.h` has the account.
- The console never reads the DMA buffer directly; it uses `capture_completed_half()`, or
  `capture_oneshot_n()` for a window nothing is writing.
- `cmd_parser.c/.h` stay unchanged from github.com/zabooh/cmd_parser (Apache 2.0), with one
  deliberate exception: `CMD_PARSER_MAX_COMMANDS` is 32 (4 bytes of RAM per slot).
  `cmd_register()` fails silently when the table is full and `help` takes a slot: prefer
  sub-commands (`stream grab`, `route list`) over new top-level commands.

## Build and verify - every change

Run from `tools\` (from the repository root every source is "No such file"):

```
build.bat              hardware (EV74H48A)  -> ..\build\adc_dma_40msps.elf/.hex
build.bat nano         EV17P63A / MPS506    -> ..\build\adc_dma_40msps_nano.elf/.hex
build.bat sim          simulator build
build.bat core         the core alone, no lab file (must stay clean)
build.bat smoke | nanosmoke    short simulator builds, see below
```

All builds must be `-Wall -Wextra` clean. Then, on every change:

```
trace.bat                  register-write/console/stub golden diff (tests/trace/scenarios
                           against tests/trace/golden); every golden must reproduce unless
                           the task says one changes, and why
hosttest.bat               tests/host/test_*.c on a host gcc, plus the Python cross-checks
python gen_core_project.py --check     core_example.X still matches adc_dma_40msps.X;
                           "stale" -> run without --check and commit the result
```

- **ISR size:** a change that touches an interrupt is checked with `python tools\fncmp.py`
  (instruction and indirect-call counts): `_DMA0Interrupt` 46/0, `_DMA1Interrupt` 41/0,
  `_U2RXInterrupt` 55/0, `_U2TXInterrupt` 48/0. A task that moves code through one states
  the new numbers.
- **Smoke run (short, about 1.5 min):** `tools\build.bat smoke`, then
  `python tools\sim_trap.py --smoke` expects `[smoke] PASS`; for the Nano
  `tools\build.bat nanosmoke` and `python tools\sim_trap.py --smoke --nano`. Run after any
  boot/console/memory-layout change. A deliberate console change:
  `python tools\sim_trap.py --smoke --update-expected` and commit the new
  `tests/smoke/expected.log` with it. The simulator raises no trap for a misaligned or
  unmapped read; a clean smoke run does not mean there is none (silicon traps).
- **Acceptance run (about 7 minutes, one at a time):** `tools\build.bat sim`, then
  `python tools\sim_trap.py --run-seconds 420` expects `[simtest] PASS`. The simulator has
  no PLL, ADC or DMA and dispatches no interrupts; it proves the ping-pong logic and
  nothing else. Keep long waits out of its path (`__delay32()` runs far slower than real time).
- **GUI:** `tools\gui_setup.bat` once, then `tools\adc_gui.bat --fake`;
  `python tools\adc_gui.py --selftest` and `python tools\gui_ui_test.py` are its checks.
- **Filter design tool:** a change under `tools/filterdesign/` runs
  `python tools\filterdesign\gui\test_codegen.py` (40 C builds, and the firmware fixtures
  `tests/host/user_filter` against a fresh `firmware.py --fixtures` - "stale" -> regenerate and
  commit them) and `python tools\filterdesign\gui\fw_ui_test.py` (browser: install, build,
  dsPIC33 GUI on the fake; it puts the default `user_filter.h` back). `--flash` programs a
  connected board: only on purpose.
- **Customer handover:** `python tools\export_core.py [--rev <commit>]` builds
  `build\core-<rev>.zip` from a commit (not the working tree) and compiles it before it says PASS.
- A change to the reply format of `version`, `help`, `status`, `regs`, `chain all` or the
  GRAB header also updates `tools/protocol.py`, `tools/eval_chain.py` and the GUI.

### MPLAB X pitfalls

- The makefile generator rewrites `languageToolchainVersion` in `nbproject/configurations.xml`
  to whatever compiler it finds first: restore that one line, never `git checkout` the file.
- After a file-list or include-path change delete `adc_dma_40msps.X/build`, `dist` and the
  generated `nbproject/Makefile-*.mk`, otherwise stale objects/lists are used.
- `src/app/version.h` (git-ignored) carries the git revision; `tools/version.bat` writes it
  (`.build-pre` hook in the project Makefile). Do not put the step into `configurations.xml`
  (`makeCustomizationPreStep`: no `Makefile-*.mk` is written then). In the hook use exactly
  `cmd /c "$(subst /,\,$(CURDIR))\..\tools\version.bat"`.
- `core_example.X` is generated from `adc_dma_40msps.X` (`gen_core_project.py`), never edited
  by hand, and uses -O1 (at -O0 the processing load doubles). `tools\_test_mplabx.bat core [nano]`
  builds it; run `gen_core_project.py` once more afterwards.
- `__builtin_write_DISICTL()` with a variable argument crashes xc-dsc at -O0: use `disi_set()`.

## Rules

- Say what has and has not run on silicon. `docs/HARDWARE-LOG.md` is the record; every board
  run and every change made in reaction to one gets a dated entry, predictions that turned
  out wrong included. A board run costs a person an afternoon: make the firmware answer as
  many open questions as possible in one pass.
- Every register value carries the datasheet (DS70005591D) page or table in the comment next
  to it; a value copied from MCC or a vendor example says so. Where the pack's ATDF and the
  datasheet disagree, the ATDF has been right every time.
- Status flags are cleared by writing the word once with 0 only in the bits to clear
  (`dma0_clear()`), never by bit-field read-modify-write; interrupt flags are cleared at the
  start of the handler, not the end.
- `FICD_NOBTSWP` and `FWDT_RCLKSEL` are pack-version dependent: written as numbers.
- Console output for humans goes through `console_puts()`/`console_kv()`, command replies
  through the parser's sink. A line longer than its buffer is a stack overrun: size buffers
  from the longest possible line and say so in the comment.
- Commit messages: what changed, why, what was verified. No attribution trailers of any kind.

## Key design facts

- **DMA `TRMODE = 1` (Repeated One-Shot), never 3.** Repeated Continuous copies a whole block
  per trigger and caused every "40 MSPS whatever the setting" and overrun storm.
- **The rate comes from PLL1, not from the CLKGEN6 divider.** `capture_set_pll(p1, p2)`:
  ADC clock = 1600 MHz / (p1 * p2); `clock_adc_set_rate()` refines it. The CLKGEN6 divider
  (`clk` command) is kept for the record; do not build a rate on it.
- **SCCP1 as the trigger:** trigger code 32 (`0x20`, "SCCP1 OC/IC Event" per the ATDF; 34 is
  SCCP3), `CCP1CON2.AUXOUT = 2` (special event trigger), `CLKSEL = 1` (CLKGEN13, PLL1 out / 2
  = 160 MHz, not the peripheral clock). Output-compare mode produced no events; use timer mode.
- **Pair mode for the triggered stream:** DMA channels 0 and 1 form the hardware ping-pong
  pair (DS70005591D 13.4.11) over a buffer of two pairs, A and B. `stream grab` moves the
  waiting channels to the other pair so the completed pair stands still while it is sent;
  the stream is never halted. A write to a running channel's `DMAxDST` moves its live
  pointer at once, so only a waiting channel is moved. `capture_service()` is never
  interrupted by a command (`uart_rx_hook()` holds bytes back meanwhile).
- `DMALOW`/`DMAHIGH` exist once; the window is the union of the ADC buffer and the generator
  table (the table lies directly below the buffer, the buffer's end stays the window's end).
  After a build `xc-dsc-objdump -h` must show ONE `.dma_buffer` section.
- `dma_overrun` is a lower bound (one status bit, counted once per interrupt entry).
- **The user filter** (`sigproc user`, 03.10.2026) is `src/core/user_filter.h`, generated:
  never edit it by hand. Its coefficients hold at `USER_FILTER_FS_HZ` only (unlike lp/hp/bp,
  which are fractions of fs). Samples go in centred (x - 2048), fixed point in the top bits
  (Q15/Q31); a gap clears the state. Its state sits in a fixed 256-byte union, so another
  filter does not move the RAM layout - the smoke `expected*.log` stay valid whatever filter is
  installed (checked 03.10.2026 with a fixed32 band-pass). Run trace/smoke/host tests with any
  filter, but commit the default unless a different default is the point. The firmware's
  `#include "user_filter.h"` finds the copy beside `sigproc.c` before any `-I`: a test with
  another header compiles a copy of `sigproc.c` next to it (`test_user_filter_xcheck.py`).
  XC-DSC's `double` is 32 bits: "double" is generated as `long double`.
- **Generator noise** (`siggen set noise <0..100>`, 03.10.2026, `lib/wavegen`): uniform white
  noise from a hash of the table index (`wavegen_noise_u()`, the same in `wavegen_model.py`),
  added after the envelope; `f0 0` = noise alone. It is a fixed, cyclic table: one FFT of it
  has a fixed line pattern, so the GUI's noise test measures with and without the filter and
  averages Welch spectra (`welch_power()`, `noise_response()` in `adc_gui.py`) - do not "fix"
  that into a single averaged FFT, it scatters by several dB. A new vector in
  `tests/ref/vectors` carries its whole command line, `--harm` included: the GUI's selftest
  reads the arguments from that header.
- Never kill `ipecmd` while it programs (03.10.2026): its java child keeps the PKoB4 and the
  tool needs a USB re-plug. Stop it only through `firmware.py` (whole tree, after 240 s).
- `sigproc` and `chain`/`test`/`dactest` judge samples themselves: run the latter with
  processing off. Measuring commands run inside `console_quiet_begin()/_end()` (polled UART
  output); a new measuring command gets the same wrapper.
- Limits measured so far (see `docs/HARDWARE-LOG.md`): clean streaming to 8 MSPS, overruns
  from about 10 MSPS, lost triggers from 16 MSPS, the ADC converts at only 18-20 MSPS in
  triggered single mode.

## Optional: remote bench

`tools/remote.py` (`RemoteBench`) drives a relay's `bench_client.py` (`flash`, `tunnel`,
`info`, `console`); its path comes from `$BENCH_CLIENT` (or `--bench-client`), there is no
default. The GUI's port selector offers "remote" for it. After every flash check the git
revision in the boot banner before trusting a result, and make sure nobody else is using the
board. `tests/host/fake_bench_client.py` stands in for it in tests, which never start a real one.
A remote run is a board run like any other and gets its `docs/HARDWARE-LOG.md` entry.
