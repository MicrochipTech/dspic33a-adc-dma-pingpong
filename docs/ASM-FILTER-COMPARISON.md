# User filter: dsPIC33A assembler against C (04.10.2026)

The filter design tool (`tools/filterdesign`) has a fifth arithmetic, **"float (32 bit,
dsPIC33A assembler)"**, generated by `tools/filterdesign/gui/asmgen.py`. This page
compares it with the C arithmetics on the board and says what was checked where.
The run is recorded in `docs/HARDWARE-LOG.md`, section 10, 04.10.2026.

## Result

On an EV74H48A board (dsPIC33AK512MPS512, 200 MHz), the same filter in three arithmetics,
`sigproc user`, CPU load from the `load=` field of the GRAB header:

| Arithmetic | Load at 1 / 2 / 3 MSPS (per mille) | Cycles per sample | Highest rate without missed halves |
|---|---|---|---|
| **float, dsPIC33A assembler** | 281 / 562 / 848 | **56** | **3 MSPS** (4 MSPS: 678 missed) |
| float (C) | 926 / 1855 / - | 185 | 1 MSPS (2 MSPS: 1304 missed) |
| fixed point 32 bit (C) | 1252 / 2507 / - | 250 | below 1 MSPS (1 MSPS: 290 missed) |

Cycles per sample = load / 1000 x 200 MHz / sample rate. They are the same at every rate.

**The assembler is 3.3 times faster than the C float code and 4.5 times faster than
fixed32.**

## Set-up

- Filter: elliptic band-pass 800-1200 Hz, order 6 (3 second-order sections), designed for
  fs = 8 kHz, section scaling on.
- Every variant was built with `tools\build.bat` (-O1) and flashed with ipecmd through the
  PKOB4. The boot banner read `git 82ed5d7+local changes`, built between 12:33 and 12:38.
- Measurement: `stream on <ksps>`, `sigproc user`, one grab to reset the counters, wait 1 s,
  then a second grab whose `load=` and `missed=` are used.
- The stream ran at 1-3 MSPS, rates the coefficients were not designed for. This does not
  affect the result, because the cost per sample does not depend on the coefficients.
- Function check at 8 kSPS with the assembler: the output stayed at 2022..2076 where the
  unfiltered input was 992..3802. `late` and `missed` were 0.

## Why the assembler is faster

| | Instructions per sample (3 sections) | Cycles per instruction (measured) |
|---|---|---|
| assembler | 33 | 1.7 |
| C float | about 90 | 2.0 |
| C fixed32 | about 175 | 1.4 |

- **Assembler:** one call per block, not one per sample. The coefficients are loaded once as
  immediates into FPU registers, and the filter state stays in registers for the whole
  block. Each section takes 7 FPU instructions (`mov.s` x2, `mac.s` x4, `mul.s` x1). The
  state update of one section is placed after the first multiply-add of the next, so the
  FPU is not left waiting for a result.
- **C float:** every sample reloads the coefficients from memory and writes the state back:
  9 memory accesses per section.
- **C fixed32:** 32 x 32 -> 64 bit multiplies (`mulss.d`), 64-bit additions done by hand, the
  intermediate result kept on the stack, and rounding and saturation in software.

**Prediction that turned out wrong:** from the instruction counts I expected a factor of
2-2.5 (45-60 against 120-130 cycles). The measured factor is 3.3, because the C float loop
costs more per instruction than assumed.

## Is C with compiler intrinsics enough?

Measured on the same board with the same design, all three variants using `fmaf()`, which
XC-DSC compiles to `mac.s`:

| Variant | Cycles per sample | Compared with the assembler |
|---|---|---|
| C stand-in from the header: a loop over the sections, coefficients and state read and written every sample | 154 | 2.7 times slower |
| C written like the assembler: coefficients and state in local variables, sections written out, one pass per block | 81 | 1.45 times slower |
| **assembler** | **56** | - |

**The intrinsic alone gains little: 185 -> 154 cycles.** Most of the gain comes from the
structure: values kept in registers, one pass per block. Well-written C gets to 81 cycles.
The remaining 25 cycles come from the compiler's register allocation and clamping:

- It keeps only 10 of the 15 coefficients in FPU registers. The others, plus 0.0 and the
  clamp limits, are reloaded as immediates inside the loop.
- It clamps with two comparisons and branches (`cpq.s`/`fbra`). The assembler uses
  `maxnm.s`/`minnm.s`, which need no branch.

## Arithmetic

The structure is the same transposed direct form II as the C float code. The difference is
that every "+ c*v" is one fused multiply-add (`mac.s`, rounded once):

    y  = b0*x + s0
    s0 = (s1 + b1*x) + (-a1)*y
    s1 = (b2*x)      + (-a2)*y

So the result is **not bit-exact to the C float code**: it differs by at most 1 LSB on the
12-bit output. It is bit-exact to C written with `fmaf()` in this order.

## What was checked, and where

| Check | Where | Result |
|---|---|---|
| Assembler against the `fmaf()` reference: every sample and the final state, 1-16 sections (every register plan), both entry points (u12 firmware, f32 Code tab), blocks of 1/7/0/256/300 samples, rails 0 and 4095 | MPLAB X simulator, `tools/filterdesign/gui/test_asm_sim.py` | bit-exact, 6300 samples |
| Assembler against the C float path of `sigproc.c` | same | at most 1 LSB |
| Firmware builds (hw, nano, core), hosttest, trace, smoke, `test_codegen.py`, `fw_ui_test.py` | PC / simulator | all pass |
| Cost per sample | board | this page |
| Frequency response against the design (dsPIC33 GUI noise test) | board | **not run** |
| Interrupts during the filter loop (FPU registers saved by ISRs) | board, indirectly: streaming with DMA interrupts at 1-3 MSPS showed no errors | no dedicated test |

The simulator gives no cycle figures. It has no timers or interrupts, and MDB's simulator
stops for good after its first breakpoint (W0101-SIM).

## Limits

- **Runs on the dsPIC33A only.** The filter design tool cannot test it on the PC: there is
  no C test bench for it. For host tests and trace builds, the generated `user_filter.h`
  contains a C stand-in with the same arithmetic.
- **Up to 3 sections (order 6), everything fits in the 32 FPU registers.** Above that, the
  remaining coefficients are loaded as immediates right before use, which costs more per
  sample. From 13 sections on, the state of the last sections is kept in memory. The
  instructions per sample from the generator are 19 / 26 / 33 / 45 / 86 / 156 / 224 for
  1 / 2 / 3 / 4 / 7 / 12 / 16 sections. Only the 3-section case was measured on the board.

## Reproduce

1. In the filter design tool, choose the arithmetic "float (32 bit, dsPIC33A assembler)" and
   press "Install into firmware".
2. Build with `tools\build.bat` and flash. Close MPLAB X first if it holds the PKOB4.
3. In the dsPIC33 GUI or on the console: `stream on 1000`, `sigproc user`, grab twice, and
   read `load=`.
4. For the comparison, install the same design as "float (32 bit)" and repeat.
5. Simulator test: `python tools\filterdesign\gui\test_asm_sim.py` (about 1 minute).
